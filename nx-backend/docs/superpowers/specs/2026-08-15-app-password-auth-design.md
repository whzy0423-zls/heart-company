# App 账号密码认证设计

## 目标

在保留现有手机号验证码登录的前提下，为 App 增加以下能力：

- 使用昵称、用户名、密码、手机号和短信验证码注册。
- 使用用户名或手机号加密码登录。
- 已存在的短信用户可以通过手机号验证码无损绑定用户名和密码。
- 注册或登录成功后继续使用现有 App Access Token、Refresh Token 和用户响应结构。

本设计只修改 App 用户体系，不复用后台管理员 `users` 表，避免 App 身份和后台权限发生耦合。

## 数据模型

扩展 `app_users`：

- `account TEXT`：用户设置的登录名。旧短信用户允许为空。
- `password_hash TEXT`：bcrypt 密码哈希。旧短信用户允许为空。
- 对 `lower(account)` 建立非空部分唯一索引，使用户名大小写不敏感且兼容旧数据。

数据库启动迁移必须同时覆盖新库和已有库：

- 在 `CREATE TABLE IF NOT EXISTS app_users` 中包含新字段。
- 使用 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 补齐已有表。
- 使用 `CREATE UNIQUE INDEX IF NOT EXISTS` 幂等创建账号唯一索引。

密码明文不写入数据库、日志、Token 或接口响应。

## 输入规则

- `account`：去除首尾空格，4 至 32 位，必须以英文字母开头，后续只允许英文字母、数字和下划线，大小写不敏感。该规则避免纯数字用户名与手机号登录标识发生歧义。
- `password`：6 至 72 字节，与当前 App 最低 6 位规则兼容，并遵守 bcrypt 输入上限。
- `phone`：现有中国大陆 11 位手机号规则。
- `code`：现有 6 位短信验证码规则，10 分钟过期且只能使用一次。
- `nickname`：去除首尾空格，1 至 32 个 Unicode 字符。

## 注册接口

新增 `POST /api/app/auth/register`：

```json
{
  "nickname": "昵称",
  "account": "username",
  "password": "123456",
  "phone": "13800000000",
  "code": "123456",
  "deviceInfo": "optional"
}
```

注册流程由 `appuser.Store` 在单个数据库事务内完成：

1. 锁定并验证手机号对应的未使用短信验证码。
2. 检查用户名是否已被其他用户占用。
3. 若手机号不存在，创建带账号、密码哈希和昵称的新用户。
4. 若手机号对应旧短信用户且尚无账号密码，为原用户绑定账号密码并更新昵称。
5. 若手机号已经绑定账号密码，返回手机号已注册冲突。
6. 标记验证码已使用并提交事务。

新创建用户的 `register_source` 记为 `account_sms`；旧短信用户绑定凭据时保留原始注册来源。

验证码消费与用户创建或绑定必须同一事务提交；任何唯一索引冲突或数据库错误都应回滚验证码状态。

注册成功后签发与短信登录相同的 Access Token 和 Refresh Token，并返回现有 `{accessToken, refreshToken, user}` 数据。

## 密码登录接口

新增 `POST /api/app/auth/login`：

```json
{
  "account": "用户名或手机号",
  "password": "123456",
  "deviceInfo": "optional"
}
```

登录流程：

1. 输入符合手机号格式时优先按 `phone` 精确查询，否则按 `lower(account)` 查询。
2. 未找到用户、用户未设置密码或 bcrypt 校验失败时统一返回“账号或密码错误”。
3. 用户状态不是 `active` 时返回“账号已被禁用”。
4. 更新 `last_login_at`，签发当前 App Access Token 和 Refresh Token。

短信验证码登录接口继续保留，不改变现有用户登录能力。

## 服务边界

`appuser.Store` 新增职责明确的方法：

- `RegisterWithPassword`：事务化验证验证码并创建或绑定凭据。
- `AuthenticateWithPassword`：通过用户名或手机号查找并校验密码。
- 复用现有 Refresh Token 存储方法。

`app_auth.go` 新增注册和密码登录处理器，并抽取统一的 App 会话签发方法，使短信登录、注册和密码登录共享 Token 生成逻辑。

`server.go` 注册两个新路由，并为 App 密码登录配置独立的账号和 IP 限流器，不与后台管理员登录限流共用。

## 错误与安全

- `400`：输入格式错误。
- `401`：验证码错误或过期、账号或密码错误。
- `403`：账号被禁用。
- `409`：用户名已存在或手机号已绑定账号密码。
- `429`：短信验证、注册或密码登录过于频繁。
- `500`：数据库或 Token 签发异常。

密码登录错误不区分用户名不存在和密码错误。服务日志不记录密码、密码哈希、短信验证码或完整认证请求体。

账号唯一性以数据库部分唯一索引为最终约束，代码中的预检查只用于返回友好错误，不能替代数据库约束。

## 隐私与后台兼容

- App 用户注销时将 `account` 和 `password_hash` 置空，同时保留现有手机号匿名化、账号禁用和 Refresh Token 撤销流程。
- 个人数据导出可以包含 `account`，但绝不包含 `password_hash`。
- 后台 App 用户列表和关键词搜索增加账号字段。
- Flutter 当前 `AppUser` 会忽略额外 JSON 字段，因此增加 `account` 不破坏现有客户端解析。

## 测试

测试至少覆盖：

- 数据库迁移对新库、旧库和重复启动均幂等。
- 新手机号注册成功并签发可用 Token。
- 旧短信用户绑定账号密码后保留原用户 ID 和业务数据。
- 用户名大小写冲突、重复手机号、错误或过期验证码均得到正确响应。
- 注册事务失败时验证码未被消费。
- 用户名登录、手机号登录、错误密码、无密码旧用户、禁用用户和限流。
- 注册与登录路由真实存在，避免 Fake Repository 掩盖 404。
- 注销后账号和密码哈希被清除，旧 Refresh Token 被撤销。
- 现有短信登录、刷新 Token 和隐私测试不回归。

## 上线顺序

1. 先部署兼容旧数据的数据库迁移和后端接口。
2. 使用真实测试手机号验证注册、用户名登录、手机号登录和旧用户绑定。
3. 再发布当前账号密码版 App。
4. 保留短信登录作为兼容和找回密码的基础能力；后续增加短信重置密码页面和接口。
