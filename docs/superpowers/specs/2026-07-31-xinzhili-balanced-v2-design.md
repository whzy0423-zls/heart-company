# 芯之力均衡提速 V2 设计

## 目标

在不改变 App WebSocket 协议、不牺牲四种会话模式差异、不中断现有双路 TTS 有序发送的前提下，缩短“用户说完”到“首段语音开始播放”的等待时间。

## 范围

本次只调整后台芯之力实时会话链路：

1. 端点判断阈值和完整句快速端点。
2. 生成回答前的上下文读取并发。
3. 流式回答送入 TTS 的文本分块大小。

不修改 App 协议，不重写 ASR/TTS provider，不改变 `audio_start/audio_end`、`assistant.done`、序列号和完整 MP3 约束。

## 设计

### 1. 模式化端点判断

默认静音阈值调整为：

| 模式 | 阈值 |
| --- | ---: |
| 抬杠候选 | 250ms |
| 正常 | 350ms |
| 安慰 | 700ms |
| 深度倾听 | 1000ms |

策略引擎记录最近一次稳定文本是否以强结束符结尾。强结束符为 `。！？!?.`，并允许其后带中文或英文闭合引号。

- 正常、抬杠模式：稳定文本完整且随后收到静音信号时，可在下一次策略 tick 直接端点。
- 安慰、深度倾听：即便句末完整，仍等待各自阈值，避免情绪表达被过早截断。
- 收到稳定文本时不直接端点，继续要求 ASR 的静音信号，避免 Paraformer 后续 final 被截断。
- 新一轮、会话重置和完成端点时清空该状态。

### 2. 上下文并行读取

保存用户消息后，同时读取：

- 会话历史与摘要；
- 用户偏好；
- 用户记忆；
- 知识库；
- 理论库。

使用标准库 `sync.WaitGroup`，所有读取共用本轮 `context.Context`。保持现有容错行为：单项读取失败按空结果处理，不导致整轮回答失败。完成后仍按“知识库优先、理论库随后”的顺序去重合并来源，再调用生成模型。

### 3. TTS 分块

流式 TTS 分块调整为：

- 首段最少 10 字后遇弱标点优先切分；
- 首段最多 20 字；
- 后续每段最多 36 字；
- 强句末仍优先切分；
- Flush 时仍发送剩余文本。

新增流式会话专用的 36 字上限，不改变通用 TTS `SplitSentences` 的 42 字行为。

## 兼容性

- WebSocket 事件名称、字段和顺序不变。
- TTS 仍最多两路并行合成，并按 `seq` 严格有序发送。
- `assistant.done`、播放确认、错误排空和单轮大小限制保持不变。
- 已保存的自定义 timing 继续生效；默认值和数据库当前配置需要同步更新。

## 验证

1. 单元测试覆盖四模式端点差异、闭合引号、重置状态。
2. 阻塞式 fake provider 验证五类上下文读取在 barrier 释放前均已启动。
3. 分块测试覆盖 10/20/36 和标点优先。
4. 运行 xinzhili、server、全仓 Go 测试及 `go vet`。
5. 合并后通过配置 GET/PUT 保留密钥语义，只更新四个 timing 值；非 Docker 重启并真机连续测试。
